# GW170817 per-EOS evidence with a NuclearMatter-Backend EOS sequence

End-to-end reference for Phase 3: feed a `nmbackend`-generated EOS sequence into
RIFT's tabular-EOS hyperpipeline to obtain per-EOS marginal evidence for GW170817.

## How the tabular method computes per-EOS evidence

The per-EOS evidence is **not a stored artifact** — it is regenerated by running CIP
(`util_ConstructIntrinsicPosterior_GenericCoordinates.py`) with a *fixed* EOS once the
intrinsic likelihood interpolant (`all.net`, built by the ILE stage) exists. The
pipeline reduces each EOS in the sequence to its stable `M → Λ` map, evaluates
`Λ(m₁), Λ(m₂)` for that EOS, and marginalizes the stored likelihood over the binary's
masses — giving the evidence for that EOS. The EOS index is itself the sampled
ordering coordinate, so one pipeline run sweeps the whole sequence.

The driver entry point is `util_RIFT_pseudo_pipe.py --internal-tabular-eos-file
<FILE>.h5`, which flows down to CIP as `--tabular-eos-file <FILE>.h5` +
`--input-eos-index N`, consumed at
`util_ConstructIntrinsicPosterior_GenericCoordinates.py` (the `EOSSequenceFromFile`
call). See `docs/rift-tabular-pipeline.md` for the full call chain.

## What this example changes

Upstream the sequence file is a precomputed posterior-sample table
(`LCEHL_EOS_posterior_samples_PSR.h5`, an `EOSSequenceLandry` HDF5). Here we instead
**generate** the sequence with our differentiable backend:

```
make sequence        # build nmb_eos_sequence.nss.h5 (+ .landry.h5) from a metamodel grid
make rundir_GW170817_nmb          # run the GW170817 tabular pipeline against it
make rundir_GW170817_nmb_legacy   # same, via the legacy Landry file (drop-in check)
```

`make sequence` calls `scripts/build_eos_sequence.py` over a small metamodel grid
(`L_sym`, `cs2_tail`). Swap in `--model rmft` or `--ingest compose:DIR` / `--ingest
cmf:FILE.csv` to drive the sequence from the RMFT solver or ingested CompOSE/MUSES-CMF
tables — the pipeline path is identical.

## Format auto-detection (no RIFT edits needed at run time)

CIP opens the sequence through `EOSManager.EOSSequenceFromFile`, which inspects the
HDF5 `representation` / `schema_version` attribute and returns:

* `EOSSequenceNMB`     — our native `NSSequence` (`representation="tabular_hc/1"`),
  stored vs central enthalpy, branch-aware; **or**
* `EOSSequenceLandry`  — the legacy format (everything else, including the LCEHL file).

Both expose the same consumer API (`oned_order_values`, `lambda_of_m_indx`,
`R_of_m_indx`, `m_max_of_indx`, `lookup_closest`), so either file type — ours or the
upstream reference — drops into the same pipeline unchanged. The two formats agree on
`Λ(1.4)` to grid resolution (verified in `tests/`).

## Requirements / notes

* Needs a working RIFT + LALSuite environment (HTCondor for the DAG). The `make`
  targets reuse the GW170817 `.ini`, `coinc.xml`, `local.cache`, and PSDs from the
  reference analysis dir (`REF=` override at top of the Makefile).
* `PSR`-only constraints are used in the reference to avoid double-counting the GW
  data; our generated sequence carries no EM/PSR prior, so it is the clean
  GW-only-likelihood × uniform-in-sequence prior case. Add an external prior via the
  `.ini` `manual-extra-ile-args` hook if desired.
* This directory is a *reference recipe*: running it requires the cluster
  environment. The sequence-generation step (`make sequence`) runs anywhere the
  backend is installed.
